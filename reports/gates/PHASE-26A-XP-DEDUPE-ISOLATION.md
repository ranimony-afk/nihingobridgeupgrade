**Scope:** `xp_events` uniqueness, `XpService.award` duplicate handling, and
`DELETE /api/xp` revocation — stop one learner's ledger row from suppressing or
disclosing another learner's award.

## C. Root cause (verified, not assumed)

| Fact | Location |
| --- | --- |
| `dedupe_key` was globally unique | `schema.ts` (pre-change), DDL `CONSTRAINT "xp_events_dedupe_key_unique" UNIQUE("dedupe_key")` |
| Duplicate fast-path queried the key alone | `xpService.ts` `award()` |
| Duplicate response returned the *existing* row's id | same, `eventId: existing.id` |
| Conflict classification matched message text | same, `message.includes("unique") \|\| message.includes("duplicate")` |

Keys are user-agnostic by construction, so collisions are **normal traffic**, not
an exotic attack:

| Producer | Key | Collides across users? |
| --- | --- | --- |
| `POST /api/xp` (fallback) | `` `${eventType}:${sourceId}` `` → `content.read:de-mizu` | **yes** |
| `POST /api/xp` (client-supplied) | any string | **yes** |
| `api/knowledge/srs` | `` `knowledge:${cardId}` `` | **yes** |
| `analyticsService.trackStudyEvent` | `` `study:${type}:${userId}:${itemId}` `` | no (already user-scoped) |
| `testService` | `jlpt-test:<sessionId>`, `jlpt-answer:<sessionId>:<qId>` | no (session-scoped) |
| `sessionService` / `srsService` | `session:<id>`, `review:<id>` | no (entity-scoped) |
| `XpService.awardDailyStreak` | `streak:<userId>:<date>` | no |

Two learners studying the same vocabulary item therefore collide on
`content.read:de-mizu`, and the first one's row silently suppresses the second's
award. Message matching also failed structurally: Drizzle wraps driver errors, so
`error.message` reads `Failed query: …` and **never** contains `unique` — the
handler never fired on the real driver error.

## D. Design and migration

* **Schema:** `dedupeKey` loses `.unique()`; `uniqueIndex("idx_xp_events_user_dedupe_key_unique").on(userId, dedupeKey)`.
  PostgreSQL treats NULLs as distinct, so keyless events stay unconstrained
  exactly as before.
* **Migration:** `drizzle/0004_xp_dedupe_per_user.sql`, produced by
  `drizzle-kit generate` (renamed to the repo's descriptive convention;
  `meta/0004_snapshot.json` + journal entry generated by the same tool):

  ```sql
  ALTER TABLE "xp_events" DROP CONSTRAINT "xp_events_dedupe_key_unique";
  CREATE UNIQUE INDEX "idx_xp_events_user_dedupe_key_unique" ON "xp_events" USING btree ("user_id","dedupe_key");
  ```

  **Safety:** the old global rule already implies per-user uniqueness, so the new
  index cannot fail on existing data; no row is read, rewritten or deleted. The
  snapshot diff touches `xp_events.indexes`/`uniqueConstraints` only. **Reverse:**
  dropping the index and re-adding the constraint is valid only while no two
  users share a key — documented, not automated.
* **`award()`:** fast-path `where (dedupe_key = ? AND user_id = ?)`; conflict
  detection via `isDedupeCollision()` (bounded `cause` walk for SQLSTATE `23505`
  **and** a constraint/index name matching `/dedupe/i`; falls back to the
  innermost driver message only when no constraint name is exposed).
* **`findEventOwner(key, userId?)` / `revokeByDedupeKey(key, reason, userId?)`:**
  optional user scope; signatures stay backward compatible for
  `sessionService`.
* **`DELETE /api/xp`:** scoped ownership lookup → foreign existence check
  (403, still zero writes) → **scoped** revoke. Unknown key keeps
  `{ success: true, revoked: false }`.
* **No producer key format changed** — existing rows stay idempotent.

form, every Phase 24 response envelope and diagnostic, every Phase 25

Changed (intended): a second learner may now hold the same key; a duplicate
response can only ever carry the caller's own `eventId`; an unrelated unique
violation now surfaces as a 500 instead of a false duplicate; `DELETE /api/xp`
performs one extra read only when the caller does not own the key.

## G. Remaining risks / follow-ups

1. Legacy rows attributed to `anonymous-user` share one namespace; they are now
   per-"user" unique like any other id. Still not HTTP-revocable (Phase 25
   fail-closed decision, unchanged).
2. `POST /api/xp` still accepts a client-chosen `dedupeKey` (now harmless to
   others) and a client-supplied `occurredAt` (backdating, N4 — open).
3. Read paths (`GET /api/xp`, `GET /api/analytics`) still accept a caller
   `userId` (N2 — open, explicitly out of scope here).
4. Foreign-key existence is still distinguishable on `DELETE` (403 vs 200
   `revoked:false`, N3 — open).
5. The TOCTOU window between the two ownership reads is benign (a row appearing
   after a `null` read can only be the caller's own) and remains untested.
6. Migration is not exercised by `drizzle-kit migrate` locally (the committed
   `drizzle.config.json` is documented as unusable); CI builds the schema with
   `drizzle-kit push`.
